== Historical Rationale for Extensions

This appendix contains the rationale for RISC-V ISA extensions at the time they
were ratified.
Unlike the ISA specification, this appendix is ordered chronologically, so as
to convey the motivation and architectural reasoning underpinning each
extension at the time of ratification.
For extensions ratified prior to the conception of this appendix (ca. 2025),
the rationale will be added over time.
In cases where the rationale was not recorded, the authors and editors will
synthesize it from the historical record.

[[smepmp_rationale]]
=== ext:smepmp[] Extension for PMP Enhancements for memory access and execution prevention in Machine mode

[NOTE]
.Terms used in this rationale
====
* *Ignored*: Any permissions set by a matching PMP rule are ignored, and _all_ accesses to the requested address range are allowed.
* *Enforced*: Only the access types permitted by the matching PMP rule are allowed; any other access raises an access-fault exception.
* *Denied*: Any permissions set by a matching PMP rule are ignored, and _no_ accesses to the requested address range are allowed; any such access raises an access-fault exception.
====

The terms _PMP Entry_, _PMP Rule_, and _Locked_ are defined in <<smepmp>>.

==== Threat model

[IMPORTANT]
.Threat Actor Profile
====
In the analysis below, Machine mode is treated as the system's trusted anchor: the adversary is malicious or compromised software running in Supervisor or User mode, together with latent bugs in Machine-mode firmware that such software may try to trigger. A Machine mode that is malicious from the outset is out of scope, as it is the root of trust and can disable any protection before locking itself down.
====

===== Overview & Scope

*1) The Confused Deputy attack scenario:* Being able to access the memory of a process running in a higher-privileged execution mode, such as Supervisor or Machine mode, from a lower-privileged mode such as User mode, is an obvious attack vector: it allows an attacker to escalate privilege and tamper with that process's code and/or data. A less obvious attack vector exists in the reverse direction: instead of tampering with a high-privileged process's own code or data, an attacker tampers with the memory of a less-privileged process and tricks the high-privileged process into using or executing it — for example, by planting code or a crafted data structure in its own memory and inducing the high-privileged process to execute or consume it.

For Supervisor mode, RISC-V already mitigates both directions: Supervisor accesses to User-marked pages are prevented unless ``sstatus.SUM`` is set (see <<sum>>), and Supervisor execution of User-marked pages is always denied (These correspond to the mechanisms commonly known as SMAP and SMEP). Without Smepmp there is no similar mitigation for Machine mode: for any physical memory region not protected by a _Locked_ rule, Machine mode has unlimited access, including the ability to execute it. Even where a _Locked_ rule is in place, it applies to both Machine mode and S/U-mode, so Machine mode cannot be isolated from S/U-mode — any region accessible by S/U-mode is necessarily accessible by Machine mode as well.

This is especially significant for RISC-V, since implementations are permitted where a hart has only Machine and User modes, so that the entire operating system runs in Machine mode in place of the absent Supervisor mode. There the attack surface is considerably larger, and attacks that in Supervisor mode are mitigated by the virtual-memory system can instead be mounted against Machine mode. Even when Supervisor mode is present, the firmware and any secure monitor running in Machine mode remain exposed.

*2) Execution from unmatched / externally-writable memory:* Machine mode's unlimited access to physical memory also extends to peripherals and, more generally, to externally-writable memory that may be under an attacker's control. This allows an attacker, for example, to place code in the memory of an external device and trick Machine mode into executing it with full privileges — for instance, tricking a buggy network driver into executing code contained in a received network packet that lives in a region outside PMP's ruleset.

*3) Introducing new executable code into Machine mode after initialization:* Firmware, and the software layered on top of it, legitimately needs to establish Machine-mode code during boot — for example, an operating system loading its kernel modules, or a platform loading trusted Machine-mode applets. Such components may create as many executable Machine-mode regions as they need, but only during initialization; once the system is initialized and starts processing untrusted input, no further Machine-mode code is expected to be loaded. The threat is an adversary that, at runtime, tries to grow Machine mode's executable code surface — loading an unauthorized module or applet, or otherwise getting new code accepted as executable in Machine mode — after the trusted boot-time code has been established.

===== Mitigations & Risk Treatment

Smepmp addresses all three scenarios by giving Machine mode its own memory access and execution controls, analogous to those that already separate Supervisor from User mode, and by letting that configuration be frozen once the system is up.

A region can be designated as belonging either to Machine mode or to the less-privileged modes, and that separation is enforced in both directions. Machine mode is denied access to memory set aside for Supervisor and User mode, so a buggy Machine mode can no longer be steered into reading or writing less-privileged data (scenario 1). Machine-mode execution is restricted to regions explicitly established as Machine-mode code; any other region, including memory with no matching protection rule at all, is non-executable in Machine mode (scenarios 1 and 2).

Finally, once firmware (or, more generally, M-mode software) initialization is complete, the configuration can be locked: the set of executable Machine-mode regions is then fixed and no new one can be introduced. This lockdown bounds the trusted code surface to what was established during boot (scenario 3). These protections are sticky, so they remain in force until the next <<reset,reset>> and cannot be lifted by subverted Machine-mode control flow.

==== Design rationale

The paragraphs below record the rationale behind the normative rules in <<smepmp>>. Where a paragraph explains a specific rule, it carries a `nonorm:` id that mirrors that rule's `norm:` id.

[[nonorm:mseccfg_mmap_op_warl]]
===== Machine-Mode Allowlist Policy
With the base specification, Machine mode can access any memory region unless it is restricted by a PMP rule with the `pmpcfg.L` bit set. This is overly permissive: although Machine mode can be restricted by adding PMP rules during the boot process, doing so can be seen as a waste of PMP rules if the number of regions to block is significantly larger than those to allow. Having the option to block everything by default and use PMP as an allowlist for Machine mode is a safer approach and offers more flexibility in such cases. It also brings symmetry between _M-mode-only_ and _S/U-mode-only_ rules, since in both cases one starts from nothing and expands the set of allowed regions. This functionality may be used during the boot process, or upon <<reset,reset>> using initial register settings (since it is a WARL field).

[[nonorm:mseccfg_rlb_op_warl]]
===== Rule Locking Bypass
Locking is inherent to _M-mode-only_ rules: the code being restricted must not be able to remove its own restrictions. However, since the adversary profile excludes malicious Machine-mode code, within a single trust domain (for example, code from one vendor) one can reasonably allow the M-mode ruleset to be edited — treating PMP as a best-effort tool for managing the attack surface, with temporary tightening, rule merging, and cleanups. That flexibility is sometimes essential: PMP rules are a scarce hardware resource, priority matching complicates rule management, and the inability to merge or clean up rules can become a blocker.

The cleaner answer is usually to run as much as possible in S/U-mode — even during early boot — where rules carry no locking property and can be managed freely without sacrificing security. That is not always practical, though: it can add significant overhead (an `ecall` into Machine mode for every ruleset change), and for single-vendor stacks that simply want to work efficiently, RLB is a useful feature. The intent is therefore that RLB is used only by vendor-specific early-boot code and disabled before control passes to the generic firmware; generic code should never run with RLB set, since RLB should never remain enabled when crossing trust-domain boundaries.

RLB also has a spec-level role: it is the only way to install an executable _Shared-Region_ rule after `mseccfg.MML` is set (see <<nonorm:mseccfg_mml_x_restrict,Code-injection prevention>>); otherwise such a rule can only come from initial register settings on <<reset,reset>>. Note that _Shared-Region_ rules are only valid when MML is set (the encodings are reserved otherwise), so we have a chicken-and-egg issue: we can't add a _Shared-Region_ rule before we set MML, and we can't add an executable _Shared-Region_ rule after MML is set, unless RLB is also set (since RLB also relaxes the "no new executable regions" part of MML). However this is an acceptable workaround, since executable _Shared-Region_ rules exist to expose vendor code to generic firmware or operating systems (see below) and are thus expected to be created by vendor-specific early-boot code, where RLB may still legitimately be used.

In short, RLB is a workaround for specific, mostly vendor-specific use cases, not a mechanism for generic code; in the general case it is a security vulnerability waiting to happen, which is why the specification carries a caution against it.

Although RLB may be used as a software discovery method for Smepmp while the PMP ruleset is still empty, given that it's meant to be used by vendor-specific code and is cleared by the time we jump to the generic firmware/OS (where software discovery actually happens), it's practically useless for this purpose.


[[nonorm:mseccfg_mml_op_warl]]
===== Machine Mode Lockdown
The base specification's dual meaning of the `pmpcfg.L` bit — marking a rule as both _Locked_ and enforced in all modes — is neither flexible nor clean. With the introduction of Machine Mode Lockdown, the `pmpcfg.L` bit instead distinguishes between rules enforced only in Machine mode (_M-mode-only_) and those enforced only in S/U-modes (_S/U-mode-only_). Rule locking becomes part of the definition of an _M-mode-only_ rule, since a rule added in Machine mode that is not locked could be modified or removed in a few instructions; S/U-modes cannot modify PMP rules in any case, so locking them does not make sense.

* *M-mode-only and S/U-mode-only rules:* [#nonorm:mseccfg_mml_pmpcfg_l_op]#Separating _M-mode-only_ from _S/U-mode-only_ rules lets us distinguish which regions are used by Machine-mode code (`pmpcfg.L == 1`) and which by Supervisor or User mode code (`pmpcfg.L == 0`), in the same way the U bit in a page-table entry marks which virtual-memory pages belong to User mode (U==1) and which to the Supervisor/OS (U==0). With this distinction in place, memory access and execution prevention can be enforced in Machine mode for any physical region that is not _M-mode-only_; this mitigates the confused-deputy scenario mentioned in the threat model.#

[NOTE]
====
Although `mstatus.MPRV` can be used in Machine mode to read/write data in an _S/U-mode-only_ region using general-purpose registers, this happens with S/U-mode permissions and honors any MMU restrictions put in place by S-mode. Machine mode can of course still tamper with the page tables or add _S/U-mode-only_ rules to bypass the protections S-mode put in place, but if an attacker has compromised Machine mode to that extent, no security guarantees are possible in any case. *The threat model assumes buggy software in Machine mode, not compromised software.* Disabling `mstatus.MPRV` was considered but deemed excessive and out of scope.
====

* *Shared-Region rules:* [[nonorm:mseccfg_mml_shared_rules_op]]Isolating Machine mode from S/U-mode leaves no way to share code or data across the privilege boundary: S/U-mode can reach only regions with a matching _S/U-mode-only_ rule, and Machine mode cannot access such regions at all. Smepmp addresses this with _Shared-Region_ rules. Shared regions come in two flavours that mirror how a region is owned and how long it lives: persistent ones, managed by Machine mode, and per-context ones, which carry the permissions of a particular S/U context and are swapped with it.
+
The most common use is Machine mode making data available to the software above it — for example exposing a device tree or ACPI tables to the generic firmware / operating system as a persistent, read-only shared region, or setting up a zero-copy data channel for a particular S/U context.
+
Sharing _code_ is also possible. The motivating case was letting a generic operating system or firmware — Linux or OpenSBI, say — call vendor-specific code without compiling it into its own image: such projects are typically built with a generic toolchain and, often by policy, will not carry vendor code they cannot build themselves. A _Locked_ shared code region lets the vendor's firmware publish a routine — for instance one that uses a vendor-specific ISA extension — that generic software can then execute directly, much as the Linux vDSO lets user space run kernel-provided code without a system call. In practice, though, this is far less common than data sharing.
+
It is worth asking why a separate rule type is needed at all, rather than simply having Machine mode drop the relevant _S/U-mode-only_ rule whenever it needs to reach the region. That approach is problematic: it works only with `mseccfg.MMAP` disabled, and it turns every access into a PMP-modifying code path — frequently exercised, easy to misuse, and fragile under re-entrancy, since an interrupt taken while the rule is removed widens the exposure window and leaves it unclear which context must restore it. More fundamentally, it would make a region's permissions an artifact of the momentary PMP state rather than a stable property of the region, blurring the ownership the rest of the design keeps explicit.
+
A coarser alternative was in fact considered: a global, `sstatus.SUM`-like bypass that would temporarily let Machine mode into S/U regions. The per-rule _Shared-Region_ approach was preferred, because a transient global permission left active on exit from Machine mode would silently void memory-access prevention.
+
Shared-Region rules reuse the formerly reserved `pmpcfg.RW == 01` encoding. An earlier draft had instead spent one of the two reserved `pmpcfg` bits (bit 5), but since those bits are a very limited resource, that approach was dropped. To keep shared data non-executable and shared code non-writable, the `pmpcfg.X` bit is repurposed: for shared data regions (except the `pmpcfg.LRWX == 1111` encoding) it marks whether S/U-mode may write, so an executable shared data region cannot be expressed; for shared code regions it marks whether Machine mode may read — and since `pmpcfg.RW == 01` already encodes the shared region, a writable shared code region cannot be expressed either.
+
The `pmpcfg.LRWX == 1111` encoding — a locked, shared, read-only data region — was decided later; its initial meaning was an M-mode-only read/write/execute region. The change was made because the already-defined shared data regions were not locked, so read/write access from Machine mode could not be restricted. Just as there are execute-only shared code regions for both modes, it was decided to also allow a least-privileged shared data region for both modes. This allows, for example, sharing the `.text` section of an ELF as a shared code region and the `.rodata` section as a locked shared data region, without letting Machine mode modify `.rodata`. A locked read/write/execute region in Machine mode was judged to make little sense and to be potentially dangerous, since Machine mode could not add further restrictions there (unlike S/U-mode, where S-mode can further restrict a `pmpcfg.LRWX == 0111` region through the MMU), leaving open the possibility of modifying an executable region in Machine mode. As a side benefit, dropping the locked read/write/execute meaning of this encoding means Machine mode can no longer encode a writable-and-executable region at all — the base PMP could still express one as RWX — giving a W⊕X property for Machine mode essentially for free.

* *Execution prevention:* [#nonorm:mseccfg_mml_exec_code]#Beyond denying Machine mode access to regions owned by S/U-mode, execution in Machine mode is also denied for any region with no matching rule at all, regardless of `mseccfg.MMAP`; this mitigates the second scenario — execution from unmatched or externally-writable memory.#

* *Code-injection prevention:* [#nonorm:mseccfg_mml_x_restrict]#For the same reason, once `mseccfg.MML` is set it must not be possible to introduce a new executable _M-mode-only_ or _Locked_ _Shared-Region_ rule, as that would allow new code to be made executable in Machine mode after lockdown. The restriction can be lifted temporarily with `mseccfg.RLB` during the boot process (see <<nonorm:mseccfg_rlb_op_warl,Rule Locking Bypass>>).#
