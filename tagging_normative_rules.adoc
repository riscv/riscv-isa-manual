= How to Tag Normative Rules in the ISA Manuals

The ISA manuals contain a mix of normative and informative (AKA non-normative) content.
We use Asciidoctor's anchor facility to tag normative text which is extracted by tools
provided in the link:https://github.com/riscv/docs-resources[docs-resources GitHub repository]
to create machine-readable and human-readable representations of normative rules.

== READ THIS FIRST

Read link:https://github.com/riscv/docs-resources/blob/main/normative-rules.md[How to Tag Normative Rules in RISC-V International Standards] for information that applies to all RISC-V International standards. This document provides information such as:

* What exactly is a "normative rule"? What is an "implementation-defined behavior"?
* How does one add normative rule tags to the AsciiDoc files using the AsciiDoc anchor facility?
* Ins and outs and gotchas when using the AsciiDoc anchor facility.
* How are the normative rules extracted from the AsciiDoc files?

== Normative Rules Overview

Each `norm:` tag in the AsciiDoc source files is one normative rule, and the rule's name is the tag's
name without the `norm:` prefix.
There is no separate definition of normative rules and no mapping between rules and tags:
one-to-many and many-to-one mappings between rules and tags are not done.
The Makefile in riscv-isa-manual generates a JSON file (machine-readable) and HTML file (human-readable) in the build directory containing all of the normative rules for the document.

== Naming Normative Rules

Normative rules should have unique, short names that are easy to put in table cells.
Normative rules related to an instruction, CSR, or CSR field should start with the instruction, CSR, or field name. Underscores should be used to separate words in rule names and tag names.
Only use a hyphen to separate words when the name in the standard contains hyphens or dots and
replace dots with hyphens (e.g., c.add becomes c-add) due to tool naming restrictions.
A hyphen has no other use: everywhere else, separate words with an underscore.

Capitalization follows the standard, not the writer.
A name that begins with an extension name uses that extension's capitalization as the
manual itself renders it, which is the extension's identifier with its first letter
capitalized (Sv48, Zicsr, Smstateen, Ssqosid, Zvknha).
Everything else in a name is lower case, including privilege modes and other
non-extension prefixes (`m_mode_...`, not `M_mode_...`; `pmp_...`, not `PMP_...`).

The single-letter extension names need care, because several of them are also the
initials of something else. `A_`, `B_`, `D_`, `F_`, `H_` and `Q_` name extensions and
keep their capital. `M_`, `S_`, `U_` and `V_` are ambiguous: `M_implies_Zmmul` is the M
extension, while `m_mode_mandatory` is machine mode, and `V_dependent_F_D` is the V
extension while `v_masked` is vector state. Decide those one at a time and prefer the
unambiguous form where one exists.

The same capitalization applies wherever an extension name appears in a tag, not only
at the front: `Zvknhb_impZvknha`, not `Zvknhb_impzvknha`.

Some hyphens look like word separators but are not, and must be left alone: the
standard's own hyphenated names (`R-type`), instruction mnemonics whose dots became
hyphens (`c-mop`, `cbo-inval`, `vsha2chl-vv`, `ntl-all`), the generic vector operand
forms (`vop-vv`, `vop-vx`, `vop-vi`) and `vmv-nr-r`. Conversely `ss_push` and `sh_enc`
begin with a shadow-stack abbreviation and an instruction mnemonic, not with the Ss or
Sh extension, so they stay lower case.

Do not distinguish rules with a bare number.
Names such as `mip_stip_stimecmp_op1` and `..._op2` say nothing about what
distinguishes the two rules, and several such names have no matching `_op1` at all.
Name each rule after the condition it covers instead (`mtval_vaddr_misaligned`,
`menvcfg_stce_zero_op`).

Tag a complete clause, not a fragment.
A tag whose text reads "`eight bytes each`" or "`read-write register`" cannot be
understood on its own, and such rules are unreadable in the extracted table.
Where a single sentence carries the size, access type and operation of a CSR, tag the
sentence once and name the tag for all of them (see `mvendorid_sz_acc_op`).

.Normative Rule Naming Convention
[options="header"]
|===
|Scenario|Format|Example
|Simple instruction|<instr>_op, <instr>_enc|add_op, c-add_op, add_enc
|Additional instruction rules|<instr>_<short-descriptor>|sll_op, sll_shamt_rv32, sll_shamt_rv64
|CSR|<csr_name>_sz, <csr_name>_acc, <csr_name>_mode, <csr_name>_op|mscratch_sz, mscratch_acc, mscratch_mode
|CSR bitfield|<csr_name>_<field_name>_sz, <csr_name>_<field_name>_acc, <csr_name>_<field_name>_op|mstatus_mpp_sz, mstatus_mpp_acc, mstatus_mpp_op
|Categories|<category>_<short_description>|br_targ, ldst_ea, R-type_operands
|Extension|<ext>_<short-description>|Sv_bare, Sv48_gigapage, Sv57_terapage, pmp_addr_match
|===

Each instruction should be covered by at least two normative rules (op & enc). _op defines the instruction operation. _enc defines instruction type and op/func fields. When one tag describes several instructions, its name lists them (e.g., `fsw_flw_op`).

Each CSR typically has at least the following rules, with text from the spec defining the size, access type, privilege mode, and operation.

* sz (size in bits)
* acc (read/write access type; relates to rw, ro, ro-h, rw-r, rw-rh from UDB)
* mode (associated privilege mode)
* op (operation, optional for CSRs such as mscratch that do not affect system behavior)

Each CSR with bitfields should have at least the following rules for each field:

* sz (size in bits)
* acc (some fields like mstatus.SD may be read-only even if the overall CSR is read/write)
* op

Reserved instructions, CSR fields, etc. use _rsv suffix.

Implementation-defined behaviors are tagged like any other normative text and follow the same naming convention.

== Tagging Normative Rules in ISA Manuals

The ISA manual builds upon the anchor naming convention of a "norm:" prefix by following it with the rule name.
Each tag is one normative rule; see the example below.

=== A Gotcha When an Inline Anchor Wraps

An inline anchor whose text wraps onto another line can silently produce no anchor at
all, with no warning, when the wrap immediately follows a bracketed construct such as
`csr::[xs]` or `ext:m[]`. The tag simply does not appear in the extracted tag file, and
the first sign of trouble is a normative rule missing from the generated normative rules.
Use the paragraph anchor form when the tagged text is a whole paragraph, and check the
extracted tags after adding an anchor that wraps.

== Example

Each tag below is one normative rule. The rules are `rv64_x_sz`, `shamt_rv64`, `lw_rv64i_op`,
`lwu_rv64i_op` and `subword_rv64i_load`.

.rv64.adoc
[source,adoc]
----
[[norm:rv64_x_sz]]
RV64I widens the integer registers and supported user address space to
64 bits (XLEN=64 in <<gprs>>).

SLL, SRL, and SRA perform logical left, logical right, and arithmetic
right shifts on the value in register _rs1_ by the shift amount held in
register _rs2_. [#norm:shamt_rv64]#In RV64I, only the low 6 bits of _rs2_ are considered
for the shift amount.#

[#norm:lw_rv64i_op]#The LW instruction loads a 32-bit value from memory and sign-extends
this to 64 bits before storing it in register _rd_ for RV64I.#
[#norm:lwu_rv64i_op]#The LWU instruction, on the other hand, zero-extends the 32-bit value from
memory for RV64I.# [#norm:subword_rv64i_load]#LH and LHU are defined analogously for 16-bit values, as are LB and LBU for 8-bit values.#
----
